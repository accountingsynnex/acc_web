# Contributing

## Getting it running

```sh
git clone <repo> && cd acc_web
npm install          # only dev tooling — the app itself has no dependencies
npm test             # lint is separate; this runs the suites
open index.html      # that is the whole "dev server"
```

The app is static files. There is no watch process and nothing to compile:
edit a file, reload the browser. `npm run serve` exists if you want it over
`http://` instead of `file://`, but both must keep working — see
`ARCHITECTURE.md`.

Sign-in credentials are in `app/auth-config.js` (the user name is in plain
text there; ask for the password).

## Before you push

```sh
npm run lint         # must be clean
npm test             # unit suites, browser smoke test, design consistency
```

CI runs all of it on every push. It does **not** currently block the GitHub Pages
deployment — that is a branch protection rule on `main` requiring the `test`
check, and enabling it is recommended.

## Making things look like the same application

Open **`app/styleguide.html`** in a browser. It shows every component with
the markup to copy, using the real `styles.css` and no local overrides, so
what you see is what you get. **If what you are about to build is already on
that page, use it — do not invent a second version of it.**

Three rules behind it:

1. **Styling classes live in `styles.css`.** No `<style>` blocks in app
   pages, no `style="..."` to change how a component looks. `btn ghost` once
   had no CSS rule at all, so its appearance was pasted inline at every call
   site — and three pages ended up with visibly different buttons.
2. **A class that exists only for JavaScript starts with `js-`.** That split
   is what lets "every styling class must have a rule" be checked by a
   machine rather than remembered by a person.
3. **Buttons come in exactly three:** `.btn` (primary), `.btn.ghost`
   (secondary), `.btn.danger` (destructive). A link inside a sentence is
   `.linkish` and is not a button — if you find yourself writing
   `style="text-decoration:none"`, you wanted `.btn.ghost`.

`npm run test:design` enforces all of it: every `.btn` on every page must
resolve to the same padding, size and radius, and match
`test/design-snapshot.json`. Restyling something on purpose means
`npm run design:update` in the same commit, which puts the change in the diff
where a reviewer sees it. Adding a component means adding it to the style
guide and, if it must be uniform, to `COMPONENTS` in `test/design.test.js`.

## The three rules that are not obvious

**1. Bump the build stamp.** `const BUILD` in `app/shell.js`, and the `?v=`
on every script and stylesheet in every `app/*.html` and `index.html`. Same
commit as your change. Without it a release lands half-cached and the
symptoms make no sense. The smoke test asserts every page agrees.

```sh
# what the bump looks like — OLD is the current stamp, NEW is yours
OLD=$(grep -oP "BUILD = '\K[^']+" app/shell.js); NEW=<today>.<n>
grep -rl "$OLD" --include=*.js --include=*.html . | xargs sed -i "s/$OLD/$NEW/g"
```

**2. Read `ARCHITECTURE.md` §4 before touching a number.** The sign
convention and the cumulative-YTD rule are assumed everywhere and stated
nowhere in the UI. A mistake in either produces statements that still add up
and are still wrong.

**3. Check `KNOWN-LIMITATIONS.md` before fixing something odd.** Several
things that look like bugs are recorded decisions. One thing that looks fine
is a real defect (§1).

## Adding a page

1. copy an existing `app/<page>.html` — the script block is the dependency
   order, there is no module system to work it out
2. `<body data-page="<name>">` so `shell.js` highlights the right nav item
3. add it to `GROUPS` in `app/shell.js`
4. add it to `PAGES` in `test/browser.test.js`

## Adding logic

If two pages need it, it goes in `engine/` — pure, no DOM, no `Store`, with
`module.exports` at the bottom so Node can require it. That is the line that
makes any of this testable. `engine/ratio-engine.js` was extracted the day
the ratio cards and the trend table started disagreeing.

Add the module's global name to the `APP` list in `eslint.config.js`, or
every use of it reports as undefined.

## Tests

`test/helpers.js` has the harness — `suite()` gives `ok/near/eq/throws/done`,
`loadApp()` wires the modules onto `global` the way `<script>` tags do.
Money is compared with `near()` to the satang, not with `===`.

A new `test/*.test.js` must be listed in `UNIT` in `test/run.js`.

Fixtures in `test/` are generated by `tools/make_sample_tb.py` from a seeded
PRNG, and CI checks they still match it. If you change the generator, re-run
it and commit the result. The figures are fabricated — no real company data
is in this repository, and none should be.

## Commits

Say why, not what — the diff already says what. Anything non-obvious that
took a while to work out is worth a sentence in the commit and, if it will
outlive the commit, a comment in the code.

## Changing the shared password

1. open `tools/set-password.html` in a browser
2. paste the four lines it prints into `app/auth-config.js`
3. bump the build stamp, commit, push

Every machine picks it up on next load; nothing to clear. Do not commit a
password used anywhere else — the repository is public and the hash is
public with it.

## Changing stored data

`localStorage` is the database and there is no migration tool, so the shape
can only change on the way in. `ARCHITECTURE.md` §5 has the procedure. The
short version: bump `SCHEMA`, add a `case` to `migrate()`, add a test that
starts from real old-shape data, and never edit an existing case.
